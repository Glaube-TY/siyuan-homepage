# 项目全局第一性原则

本项目的所有功能都必须以"不破坏用户原有环境"为第一前提。插件可以增强思源的使用体验，但不能改变思源本体、用户主题、其他插件或用户文档的既有行为；任何功能、样式、数据读写和自动化操作，都必须限定在明确的插件作用域内，并且尽量可解释、可回退、可关闭。

## Kernel / SQL 查询安全原则

大库环境下，对 `blocks.content`、`blocks.markdown`、`blocks.fcontent` 使用 `LIKE '%关键词%'` 会触发全表扫描，导致 kernel 内存和 CPU 压力显著上涨。本条为全局高优先级限制：

1. 插件内置 SQL、后台任务、主页组件、Agent 工具等不得使用 `blocks.content`、`blocks.markdown`、`blocks.fcontent` 的 `LIKE '%关键词%'` 作为正文搜索条件。
2. `LIMIT`、分页、字段收窄只能减少返回结果量，不能避免数据库扫描成本，不能作为 `content LIKE` / `markdown LIKE` / `fcontent LIKE` 的安全替代。
3. 正文关键词搜索必须优先使用 `blocks_fts` 的 `MATCH` 查询，或使用思源官方搜索 API 的分页能力。SiYuan 的 `blocks_fts` 已使用 `tokenize='siyuan_case_insensitive'`，无需再使用 `blocks_fts_case_insensitive`。
4. 任务状态、历史标记等结构性判断应使用窄范围查询（如 `subtype = 't'`、`root_id = '...'`）后在前端解析，禁止用全库 `markdown LIKE` 做前缀/子串扫描。
5. `path`、`ial`、`tag`、`bookmark` 等非正文元数据字段使用 `LIKE` 时必须限定业务范围、转义输入、设置返回上限，并确认不会形成大库正文扫描。
6. Agent SQL 工具也必须遵守本条；对违反上述限制的只读 SQL 应拒绝执行并提示改用 FTS 或更窄的结构化条件。

## 样式隔离原则

插件样式只能影响插件自己的界面，不能污染思源全局样式、默认主题样式、用户自定义主题或其他插件界面。

使用思源内置组件类和主题变量时，必须先确认它们是真实存在且稳定的思源样式能力。可以复用思源的基础类名和 CSS 变量来保持视觉一致，但不能在插件中全局覆盖 `.b3-button`、`.b3-text-field`、`.b3-switch` 等思源通用组件类，也不能定义过于通用的全局类名影响外部页面。

所有自定义样式都应绑定在插件根容器、功能模块容器或组件局部类名下。必须避免无作用域的全局选择器，避免直接重写 `body`、`:root`、`.layout`、`.b3-*` 等全局对象。确实需要全局样式时，必须说明原因，并尽量使用插件专属前缀和最小影响范围。

当样式需要适配主题时，应优先使用思源默认主题中真实存在的 `--b3-*` 变量；不确定是否存在的变量必须提供 fallback，不能假设所有主题都会提供同名变量。插件不能依赖私有、临时、非标准或只在某个主题中存在的变量作为核心样式基础。

## 数据层与设备视图层

业务数据与前端视图必须分层：任务、项目、纪念日、记账、收藏等业务数据跨设备共享，由统一服务读写；PC 主页和侧边栏按物理 PC scope 独立保存，移动主页使用固定 `mobile-shared` scope。

当前前端只能精确读写自己被授权的 `scope + surface` 视图目录，禁止扫描、回退、合并或修改其他设备配置。组件文件只能保存实例与展示参数，不得复制业务数据。

业务数据异常只能影响对应组件，视图配置异常不得覆盖业务数据，也不得清空整个主页。

## Agent 语言无关原则

Agent 系统的架构设计必须保持语言无关，严禁在运行时通过对用户输入或模型生成文本的自然语言词法/语法/模式匹配来进行控制流决策：

1. **禁止自然语言控制流**：禁止运行时根据用户问题或模型正文中的中文、英文、日文或其他自然语言关键词、正则、前后缀、词表来判断用户意图、工具需求、澄清状态、完成状态、重试策略或最终状态。
2. **结构化决策归属模型与 Tool Contract**：工具选择由模型依据 Tool Schema、系统提示词和 Provider 原生 `tool_calls` 表达；执行安全、权限与恢复只读结构化 `tool_result`、事件（`AgentWorkbenchEvent`）、错误码（`code`）、版本（`revision`）和结构化 Observation。
3. **正式语法与安全检查边界**：块 ID/文档 ID、URL、JSON、XML/DSML 语法解析、SQL/Shell 只读与注入防护、凭据脱敏以及用户明确发起的搜索/过滤功能，属于正式语法或数据处理边界，不属于自然语言控制流禁令。
4. **多语言支持机制**：多语言支持依靠模型本身的多语言能力以及系统的结构化本地化资源（i18n / metadata），不得为特定语言维护业务意图词表或启发式规则。

## 通用 Agent 架构原则

1. **全局提示只说明身份、环境、能力和工具边界**：Agent 必须保持通用、简洁和语言无关。全局提示只声明身份、运行环境、可用能力与工具使用边界，不得累积具体业务流程、历史故障补丁、测试步骤或特定问题的处置规则。
2. **工具调用由模型决定，模型误用优先优化提示与 Schema**：工具必须通过名称、简短用途、输入 Schema、返回契约和结构化错误码把能力说明清楚；工具选择、调用顺序和参数组合由模型依据这些契约自行决定。模型调用错误属于模型行为，经常误解时先精简或修正系统提示、工具描述与 Schema，不得用自然语言关键词、正则、词表或问题专用分支替模型决策。
3. **确定性安全约束由 Runtime 强制**：只有权限、数据安全、只读保护、写入校验、CAS/版本核对等确定性不变量才由运行时强制执行。
4. **链路稳定性问题修共享边界，不针对特定问题打补丁**：如果问题来自传输、状态恢复、上下文、工具执行、超时、重试、去重或终态交付等链路稳定性，必须修复共享链路根因，不得识别某种用户问题或正文措辞后打补丁。
5. **规则分层与去重**：新增 Agent 规则前先判断它属于提示与工具契约、确定性运行时约束，还是单次任务要求；单次业务要求不得进入全局 Agent 架构。优先删除过时规则和重复提示，不建立平行判断层。
