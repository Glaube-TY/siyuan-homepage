# 主页插件大版本产品方向与功能路线（2026-08-12）

本文记录已经确认的产品方向、明确暂缓/不考虑的事项，以及仍需后续讨论的候选。记录目标不是罗列功能名称，而是保存每项功能想解决的问题、预期体验、实现边界和与现有架构的关系，避免后续开发逐渐偏离原始目标。

后续设计和开发必须遵守项目现有的注册入口、设备视图边界、主题框架、组件样式框架和数据服务边界。新增功能应尽量注册到已有体系，不得因为单个功能建立一套平行且孤立的配置、样式或业务数据实现。

## 优先级定义

- **P0｜当前大版本主线**：本次大版本发布前后的主要架构与体验优化。
- **P1｜明确要做的核心能力**：方向已经确认，应作为后续连续开发的重点；具体实现仍可分阶段讨论。
- **P2｜明确保留、逐步推进**：确定有价值，但依赖前置架构、外部数据源或需要逐组件建设。
- **暂缓/不考虑**：当前明确不作为开发方向；除非出现新的高价值场景，否则不重新启动。
- **建议候选**：由本轮分析提出，尚未由产品方向确认。

## P0｜当前大版本主线

### 1. 设置发现与信息架构

#### 目标

在功能数量持续增长后，解决用户“知道有这个功能，但不知道在哪里设置”“无法判断设置影响哪个设备或主题”的问题。

#### 明确范围

- 为整个主页设置提供全局搜索。
- 搜索对象不是页面标题，而是具体设置项；结果应显示设置名称、简短说明、所属路径和作用域。
- 点击结果后直接打开对应设置页、滚动到目标项并短暂高亮，不能只停留在大分类入口。
- 为设置项声明作用域，例如：全部设备、当前设备、当前视图、当前主题、当前组件实例。
- 作用域必须来自设置项注册元数据，不能靠搜索页面重复维护一份映射表。
- 实时保存机制保持不变，不显示打断操作的全局消息。
- 设置页右上角可以在修改发生后短暂显示“保存中”“已保存”“保存失败/同步失败”；稳定后自动弱化或消失。
- 保存失败状态必须可点击查看原因或重试，不能只改变图标颜色。

### 2. Agent 执行体验

Agent 是本次大版本需要重点继续设计的方向。后续结合成熟 Agent 产品单独讨论并确定：

- 一轮执行的明确阶段，以及用户如何判断 Agent 仍在工作还是已经停止。
- 模型推理、工具调用、等待确认、继续生成、完成、取消、失败等状态的信息层级。
- 工具执行过程如何折叠展示，既不刷出大量过程文字，也不隐藏关键动作。
- 工具失败、模型不继续、超时、中断、配置不支持工具调用等错误的差异化反馈。
- 重试本轮、从失败步骤继续、切换模型、打开配置、复制诊断信息等恢复动作。
- 会话恢复、持久化和历史压缩状态如何被用户理解，而不是只存在于内部实现。

本节暂不确定最终 UI，后续应形成独立的 Agent 交互设计方案。

## AI Agent 平台专项（横跨 P0 与 P1）

这一专项不是新增一个聊天页面，而是把当前分散在 AI 对话、主页状态语、文档选中文字处理和机器人中的能力，收敛为一套可评测、可恢复、可扩展、可审计的 AI 平台。不同入口保持各自轻重和交互形态，但共用稳定的底层能力。

### 当前实现基础与主要缺口

经本地代码核对，当前 Agent 并非从零起步，已经具备以下基础：

- 桌面端对话和机器人已经复用 `NativeToolAgentLoop`，不是两套完全独立的 Agent 循环。
- 已有模型提供商适配、原生工具注册、权限确认、取消、超时、最大工具调用次数和完成/失败/取消状态。
- 会话可持久化，工具大结果会按类型压缩；当前上下文保留最近 10 轮原文，并维护阶段摘要、最近操作结果、目标文档/块索引和活动工作目标。
- 阶段摘要已有上下文压力判断：根据未总结轮次和上下文使用率产生 suggested、recommended、urgent、required 等状态。
- 已有执行中任务日志、最近 trace、模型 Agent 兼容性诊断、工具结果摘要以及部分面向用户的错误映射。
- 全局记忆写入已经具备并发摘要校验、写后回读和一致性验证，数据安全基础较好。
- 状态语和选中文字处理已走独立的轻量文本生成路径，说明项目已经具备“不同入口使用不同执行形态”的雏形。

当前最主要的问题集中在四个方面：

1. **上下文机制有实现，但缺少可证明的长期连续性。** 最近轮次、阶段摘要和操作记忆都有固定字符/条数上限，但尚未形成“哪些信息必须保留、哪些可按需取回、压缩后是否仍然正确”的可测协议。
2. **错误能被识别和展示，但恢复策略还没有统一。** 当前错误映射较丰富，机器人也有超时保护，但还缺少贯穿模型、工具和写操作的统一错误分类、重试条件、幂等判断与安全续跑检查点。
3. **全局记忆的存储安全强于语义能力。** 目前一条记忆基本等于文档中的一个段落，缺少作用域、类型、证据、置信度、冲突、过期、替代、遗忘和相关性检索，无法自然成长为个人 AI 助手。
4. **已有多种 AI 入口，但缺少统一能力契约和统一评测。** 各入口可以调用模型，却还不能用同一套标准证明它们在正确性、稳定性、成本、权限和记忆行为上符合预期。

### 平台目标架构

后续以一个共享的 Agent Kernel 为中心，每个入口只注册自己的 Profile，不再复制完整执行逻辑。当前“本地知识库 Agent 对话”是已有能力最完整、最适合作为抽取起点的参考实现，但不应让其他入口直接依赖它的页面、Svelte 状态或 Workbench UI。正确关系是：从它下面抽出通用内核和能力注册层，然后本地知识库对话也成为这套内核上的“全功能 Profile”。

这与主题系统的注册思想一致：主题通过统一契约注册 token、组件类别和展示变体；Agent 入口则通过统一契约注册模型调用、上下文、工具、记忆、MCP、技能、权限和执行策略。新增入口只进行装配，不重新编写一套对话、工具循环或错误恢复方法。

#### 分层能力栈

Agent 不是只有“普通对话”和“完整 Agent”两个档位，而应拆成可以逐层组合的能力：

1. **模型生成层**：统一单轮生成、流式生成、取消、超时、Provider 适配、错误归一化和用量记录。状态语、摘要、分类等轻任务只需要这一层。
2. **上下文对话层**：在模型生成之上增加多轮会话、上下文预算、阶段摘要和持久化。普通连续对话使用到这一层。
3. **工具 Agent 层**：增加 Agent 循环、工具选择、参数校验、权限确认、工具结果回传和安全恢复。入口可以只注册它真正需要的工具集合。
4. **知识与记忆层**：按需增加知识库检索、会话工作记忆、全局长期记忆、项目记忆和来源引用。长期记忆的读取和写入必须分别授权。
5. **扩展能力层**：按需增加 MCP、Skills/技能、网页能力、本地工作区能力和组件领域能力。每项扩展独立注册，不能因为启用了完整 Agent 就自动全部开放。
6. **自治执行层**：在上述能力上增加后台 Job、定时任务、心跳、检查点和恢复；这是权限最高的一层，只对明确场景开放。

因此，“本地知识库 Agent”不是一套要被其他功能整体复制的巨大实现，而是上面六层能力的完整组合；其他功能可以从最底层开始，按需求逐层增加。

#### 共享 Agent Kernel

统一提供：

- 模型与 Provider 能力协商。
- 工具注册、参数校验、权限确认和结果协议。
- 上下文预算与按需检索。
- 短期工作记忆、长期个人记忆和知识库检索。
- 执行检查点、取消、恢复与失败归因。
- trace、诊断、评测数据和成本/延迟统计。
- 后台 Job、定时任务和心跳任务的执行入口。

#### Agent Profile

每个 AI 入口注册以下元数据：

- `id` 与用途，例如 chat、selection、status、robot、homepage、background-job。
- 系统约束与输出契约。
- 可用上下文提供者和工具白名单。
- 长期记忆的读写策略。
- 是否流式、超时、最大步骤、最大成本和模型档位。
- 权限等级、远程调用限制和需要人工确认的动作。
- 失败后的允许恢复动作。

这样既共享稳定内核，也不会把状态语生成这种轻任务强行做成完整 Agent。

#### 能力注册与装配规则

为了避免后续再次出现“每个地方各写一套”，通用框架至少应提供以下可注册契约：

- `ModelGateway`：统一模型选择、Provider 适配、单轮/流式生成、取消、超时、错误和用量。
- `ConversationStore`：会话消息、压缩摘要、检查点和恢复数据的存取。
- `ContextProvider`：当前文档、选中文字、主页组件、机器人会话、知识库等上下文来源。
- `ToolProvider`：一组具有 schema、读写属性、风险等级、幂等性和权限要求的工具。
- `MemoryProvider`：会话记忆、项目记忆和全局记忆；分别声明读、候选写入和正式写入权限。
- `KnowledgeProvider`：全文检索、知识地图、向量/关键词检索和引用解析。
- `SkillProvider`：内置技能、用户技能及其提示模板和允许调用的能力。
- `McpProvider`：MCP Server 和工具索引；由 Profile 明确选择允许的 Server/工具，不能继承全部配置。
- `PermissionPolicy`：用户确认、远程调用、敏感数据、写操作和高风险动作规则。
- `ExecutionPolicy`：最大步骤、并行性、重试、超时、成本预算、模型档位和后台运行限制。
- `TraceSink`：所有入口使用同一 trace、correlation id、诊断和 eval 采样协议。

Profile 是这些能力的声明式装配结果，而不是一个包含大量 `if (isRobot)`、`if (isSelection)` 的中央函数。创建新入口时只声明“使用哪些能力、采用什么策略”，由统一 Composition Root 构造本轮运行环境。

能力必须遵守最小授权和显式依赖：

- 注册工具循环不等于开放全部工具；工具必须由白名单或能力包加入。
- 开放长期记忆读取不等于允许写入；候选记忆写入与正式晋升也要分离。
- 开放 MCP 不等于信任全部 MCP 工具；Server、工具和读写权限分别控制。
- Skills 只能引用当前 Profile 已开放的上下文和工具，不能通过技能绕过权限。
- 机器人、后台任务等非本地交互入口默认采用更窄的权限和数据作用域。
- Profile 和能力契约需要版本号；升级时由框架完成兼容检查，不能由各入口自行猜测字段。

#### 现有入口的复用现状与迁移原则

当前代码已经出现了正确方向的基础：

- 本地知识库对话通过共享 Provider 工厂、`AgentSession`、`NativeToolAgentLoop` 和每轮工具 Registry 组装完整执行环境。
- 机器人已经直接复用 `NativeToolAgentLoop` 与 Provider 工厂，再对允许工具做远程安全过滤。这证明“共享内核 + 入口 Profile”在现有代码中可行；后续应把它的工具、上下文、记忆、MCP 和 Skills 差异改为声明式 Profile，而不是继续手工补功能。
- 状态语和划词 AI 当前走轻量文本生成路径，这个形态本身正确；它们应接入统一 `ModelGateway`、错误、trace 和预算协议，而不是为了统一而强行进入多步工具循环。
- 本地知识库已有的全局记忆、MCP、Skills、知识检索等能力需要从 Workbench 装配中解耦为独立 Provider，之后其他入口才能按需选择，而不是复制实现或只能全部开启。

迁移过程中坚持“先抽象现有稳定实现，再迁移入口”，不一次性重写 Agent：

1. 标记现有共享内核、WorkBench 专属逻辑和 UI 状态边界。
2. 先统一 ModelGateway、错误协议、trace 和取消/超时。
3. 将工具 Registry、上下文、记忆、知识、MCP 和 Skills 分别变成 Provider。
4. 把本地知识库对话改为全功能 Profile，保证行为不变并以现有 eval 回归。
5. 把机器人改为远程受限 Profile，删除其可以由通用装配替代的平行代码。
6. 将状态语和划词接入轻量 Profile，只共享它们需要的层级。
7. 后续主页智能卡片、知识管家和后台 Job 只能通过这套注册入口接入。

### P0：对标成熟产品的 Agent 内核验证

对标重点不是模仿 Claude Code 或 Codex 的界面，而是验证它们所代表的成熟 Agent 方法：有限上下文下的高信号信息组织、工具结果驱动的连续执行、明确自治边界、可观察 trace，以及用代表性任务反复测量真实结果。

#### 上下文记忆管理

目标是保证 100 轮对话之后，Agent 不是机械携带全部原文，而是仍能正确处理关键事实、用户后续修正、未完成承诺和已经验证的工具结果。

上下文分为五个预算区：

1. **不可压缩区**：当前系统策略、用户明确约束、安全规则、当前任务目标和审批状态。
2. **近期原文区**：保留最近若干完整轮次；当前已有最近 10 轮基础，后续应根据模型窗口和任务压力动态调节。
3. **工作状态区**：活动目标、待完成步骤、最近可靠工具结果、写操作状态、用户最新修正和未解决问题。
4. **分层摘要区**：按任务阶段生成摘要，再将多个阶段摘要合并为更高层摘要；摘要必须记录覆盖范围和来源 turn id。
5. **按需检索区**：旧对话、原始工具输出和历史文档不常驻上下文，只保存可检索引用，需要时通过关键词、语义、时间和实体条件取回。

必须新增“上下文清单”诊断信息，至少记录每次请求注入了哪些类别、字符/token 占用、被排除的原因以及摘要覆盖到哪一轮。该信息默认不打扰用户，但可以在诊断面板查看。

100 轮连续性验收场景至少包括：

- 第 1 轮给出的稳定偏好，在第 100 轮仍可按需回忆。
- 第 20 轮事实被第 60 轮明确修正后，只采用最新有效版本。
- 第 30 轮开始但未完成的任务，在压缩后仍知道剩余步骤。
- 写工具已经成功、失败或结果未知时，不会在压缩后虚构成另一种状态。
- 被压缩的文档正文需要再次使用时，Agent 会重新读取，而不是把旧摘要当成原文。
- 长对话中不同项目/文档的上下文不会串线。

#### 工具执行异常与安全恢复

建立统一错误协议，不能只返回 `ok=false + message`。每个模型/工具失败至少包含：

- `category`：参数错误、权限拒绝、网络/限流/超时、Provider 协议、工具不存在或 schema 不匹配、业务冲突、数据版本过期、部分写入/结果未知、用户取消、循环超限、安全阻止。
- `retryable` 与可选 `retryAfter`。
- `safeToReplay`：是否可以安全重放。
- `sideEffectState`：`not_started`、`committed` 或 `unknown`。
- `userAction`：补充参数、授权、重试、切换模型、人工检查或无法自动恢复。
- `correlationId`：将 UI、trace、Provider 请求和工具执行串起来。

恢复规则：

- 仅对明确可重试且幂等的瞬时错误做有上限的指数退避；不能对所有失败无脑重试。
- 对写操作结果未知的情况先回读验证，禁止直接重放，以免重复创建或覆盖。
- 每次工具执行前后建立轻量检查点，保存已完成步骤、待执行动作和副作用状态。
- 工具失败后必须把结构化结果返回模型，使模型能改参数、换工具、降级或向用户询问。
- UI 必须区分“正在重试”“等待用户确认”“部分完成”“可从失败步骤继续”和“必须重新开始”。
- Provider 不支持原生工具、流式协议异常、模型输出中断等问题应归到 Provider 能力层，不让业务工具承担错误。

#### Agent 评测体系

发布前的“自己多用一段时间”仍然保留，但不能作为唯一验证方式。建立可重复运行的 Agent eval，并优先从历史真实故障、控制台日志和人工回归用例中整理第一批 20～50 个任务。

评测套件包括：

- 多轮上下文：回忆、修正、冲突、阶段摘要和 100 轮压缩后连续性。
- 工具选择：是否选择正确工具、参数是否完整、是否避免伪造工具调用。
- 故障恢复：超时、限流、断流、权限拒绝、无效参数、工具不存在、写后结果未知。
- 写操作真实性：最终数据库/文档状态是否正确、是否重复写、回复是否与真实结果一致。
- Provider 兼容性：不同模型的工具调用、继续生成、截断、空响应和多工具行为。
- 记忆：候选提取、去重、冲突替代、遗忘、相关性召回和错误记忆拦截。
- 知识库：检索来源、引用一致性、无答案时是否承认不足。
- 多入口：聊天、选中文字、状态语、机器人、主页卡片和后台 Job 的权限/上下文隔离。

每个任务保存输入、初始状态、允许工具、执行 trace、最终环境状态和评分结果。评分优先验证环境最终状态，而不是只判断 Agent 最后的自我陈述。

核心指标：任务成功率、回答完整度、错误事实率、工具失败恢复率、写操作一致性、多次运行稳定性 `pass^k`、延迟、token/成本、工具调用次数、长期记忆精确率/召回率和上下文修正命中率。确定性断言、模型评分和人工抽查组合使用，模型评分不能替代可程序化验证的结果。

### P1：可持续进化的个人 AI 记忆

#### 核心决策

不再把“指定文档中的若干段落”直接等同于完整记忆系统。现有文档可以继续作为用户可读、可编辑的记忆审阅界面，但长期记忆的权威状态应改为结构化数据；文档作为结构化记忆的投影或同步视图，不能继续兼任唯一数据库。

#### 记忆分层

1. **身份与稳定资料**：用户明确提供且长期稳定的信息。
2. **偏好、约束与目标**：写作偏好、工作方式、长期目标、明确禁忌和授权边界。
3. **项目/会话工作记忆**：当前项目状态、决定、未完成事项和临时假设，默认不永久保存。
4. **情景记忆**：完成过的任务、可靠工具结果和重要决策，可按时间和对象检索。
5. **语义记忆**：从知识库提取的实体、主题与关系，只保存索引和证据引用，不把整篇笔记复制进提示词。
6. **原始会话档案**：用于追溯和按需检索，不自动全部注入新会话。

#### 记忆记录模型

每条记忆至少包含：

- id、内容、类型和作用域（用户/项目/会话/入口）。
- 状态（候选、有效、已替代、已拒绝、已过期）。
- 来源 turn、文档或工具结果的证据引用。
- 置信度、重要性、创建时间、最后确认时间和可选有效期。
- 标签/实体、冲突对象、替代关系和是否被用户固定。
- 敏感等级与允许在哪些 Agent Profile 中使用。

#### 记忆生命周期

采用“两阶段”机制，而不是模型想到什么就直接写入长期记忆：

1. 从用户明确表达、重复行为、工具执行结果和任务 trace 中产生候选记忆。
2. 先写入会话级暂存区，记录证据和置信度。
3. 会话结束或后台整理时做去重、合并、冲突检测、稳定性判断和敏感信息过滤。
4. 高影响、敏感或推断性内容需要用户确认；低风险且证据充分的偏好可以自动晋升，但必须可撤销。
5. 晋升为长期记忆后，只在与当前任务相关时检索注入。
6. 长期未使用、已有新证据否定或具有有效期的内容进入过期/待确认状态，而不是永久积累。

严禁通过一次偶然表达就推断疾病、政治倾向、财务状况、亲密关系等敏感人格资料。AI 可以主动发现“可能值得记住”的内容，但用户必须能看到“为什么记住、来自哪里、在哪些地方使用”，并能编辑、删除、固定、禁止记忆或要求忘记。

#### 记忆体验

- 在设置或独立记忆中心展示候选、有效、冲突、待确认和已过期记忆。
- 对每条记忆提供来源、最近使用时间和“为什么本轮使用了它”。
- 对话中支持自然语言指令：记住、不要记住、仅本次使用、修改这条记忆、忘记与某主题有关的内容。
- Agent 可在合适时提示“我发现一个可能长期有用的偏好，是否保存”，但不能频繁打断。
- 允许导出、备份和彻底清理；删除后不能继续从旧摘要偷偷恢复。

### P1：LLM Wiki / AI 知识管家

这里的 `LLM Wiki` 暂作为需求名称，目标是让 AI 全面理解并辅助治理思源知识库；如果后续指的是某个具体项目或协议，再单独评估兼容方式。它不是简单的 RAG 问答，也不是让 AI 自动改写全部笔记。

#### 核心能力

- 建立主题、实体、人物、项目、概念和时间线的知识地图，并关联到原始文档/块证据。
- 为文档生成可更新的 AI 元数据：摘要、关键结论、实体、日期、任务、状态、来源和置信度。
- 发现可能的关联、缺失链接、重复内容、相互矛盾的结论、长期未更新内容和知识空白。
- 形成“知识整理收件箱”，将建议以来源、理由和预览差异呈现，由用户批量接受、拒绝或稍后处理。
- 支持从多个文档生成带引用的主题简报或动态 Wiki 页面；每个结论必须能回到原文证据。
- 定时或在知识库变化后增量刷新索引与摘要，不能每次全库重算。
- 将知识库中的任务、项目、人物和事件暴露给日历、强化日记、临时工作台与 Agent，但通过统一领域接口读取。

#### 数据与安全边界

- 确定性索引（文档、块、引用、标签、时间、数据库字段）与 AI 推断（主题、摘要、关系、冲突）分层保存。
- AI 生成内容必须带生成时间、模型版本、来源和置信度，不能冒充用户原文。
- 默认采用“建议 → 预览 → 应用”，不静默覆盖手写笔记；批量操作可撤销并保留变更记录。
- 删除、移动、大规模重写等高影响操作必须人工确认。
- 已有知识地图读取、全文检索和 Agent 工具应作为基础能力继续扩展，不再另建平行的全库扫描实现。

#### 首期落地范围

1. 文档 AI 元数据与增量索引。
2. 主题/实体知识地图和来源跳转。
3. 重复、冲突、缺链和陈旧内容建议。
4. 知识整理收件箱与可撤销应用。
5. 带引用的主题简报。

首期不做“AI 无需确认自动重构整个知识库”。

### P1：主页的全方位 Agent 接入

主页是信息聚合和行动入口，不应在每个组件里重复放一个聊天框。接入方式以“能力注册 + 安静的智能表面”为主：

- **今日简报**：根据日历、任务、习惯、强化日记、专注和知识库变化形成可追溯摘要。
- **智能工作台卡片**：Agent 根据当前目标临时生成可操作卡片，沿用已经确认的临时智能工作台方向。
- **建议收件箱**：集中显示知识整理、任务风险、日程冲突、遗忘事项和可执行建议，避免弹窗打扰。
- **组件上下文动作**：组件注册“询问此内容、总结、创建任务、安排日历、开始专注”等能力；通过右键或已有操作入口触发，不新增常驻悬浮按钮。
- **后台任务结果**：定时任务和心跳任务在主页展示摘要、异常和需要确认的动作，不展示冗长执行日志。
- **跨组件任务编排**：用户用自然语言提出目标，Agent 调用已注册领域能力完成操作，优先于要求用户维护大量手工规则。

每个组件如需被 Agent 使用，应通过统一注册入口声明：

- `AgentContextProvider`：可以向 Agent 暴露什么数据、数据作用域和敏感等级。
- `AgentActionProvider`：允许执行哪些动作、读写属性、幂等性和确认要求。
- `AgentCardTemplate`：哪些结果可以被临时工作台安全渲染和操作。

用户应能查看一次 Agent 行动使用了哪些主页数据，并在全局、设备、组件或单次任务层面关闭授权。主题只控制这些智能表面的视觉表现，不能改变权限和业务含义。

### 各 AI 入口的定位与边界

| 入口 | 执行形态 | 默认上下文 | 工具与记忆策略 |
| --- | --- | --- | --- |
| 本地知识与对话 | 完整 Agent | 当前会话、知识库检索、相关长期记忆 | 可使用完整授权工具；支持多步骤、确认、恢复和阶段摘要 |
| 自动状态语 | 单次轻量生成，不进入完整 Agent 循环 | 仅用户选择的真实统计事实与风格配置 | 只读、无长期记忆写入、缓存/防抖、失败回退到上次成功或普通状态语 |
| 文档选中文字 AI | 默认无状态的局部处理 | 选中文字、技能提示和必要文档元数据 | 默认无工具和长期记忆；“在对话中继续”时显式转入完整会话 |
| 机器人 Agent | 共享 Agent Kernel 的远程受限 Profile | 机器人会话、明确授权的知识与相关记忆 | 工具白名单更窄、超时更严格、写操作确认和远程身份审计；继续复用共享循环 |
| 主页智能表面 | 摘要、建议或临时工作台 | 用户授权的组件快照与当前主页作用域 | 通过组件能力注册调用；默认先建议，写操作按风险确认 |
| 定时/心跳任务 | 后台 Job Profile | 固定任务输入、上次检查点和最少必要记忆 | 有成本/次数/时间预算；产生可审计结果，不能无限自主循环 |

### Agent 平台实施顺序与验收门槛

1. 先把现有 trace、错误码、会话压缩和多入口调用整理成统一 Profile/错误协议，不先大改 UI。
2. 建立第一批真实失败 eval，覆盖“模型说下一步但停止”、工具失败、断流、写入未知、100 轮上下文和机器人超时。
3. 增加上下文清单、分层摘要和历史按需检索；用 eval 证明压缩前后结果没有明显退化。
4. 将全局记忆升级为候选 → 会话整理 → 长期记忆 → 相关检索 → 衰减/遗忘的生命周期，并保留用户审阅面。
5. 将聊天、状态语、选中文字和机器人正式注册为不同 Agent Profile，统一诊断与权限协议。
6. 实现主页 AgentContextProvider/AgentActionProvider 注册层，再接今日简报、建议收件箱和临时智能工作台。
7. 在统一索引与记忆基础上实现 LLM Wiki / AI 知识管家首期。
8. 最后接入定时任务、心跳任务和更高自治能力；自治范围必须由评测结果和权限模型逐步放开。

每一阶段必须同时满足：构建/类型检查通过、关键 eval 无回归、真实环境最终状态正确、失败可解释、取消后不继续写入、诊断信息中不泄露密钥和不必要正文。

### 3. 组件与主题的体验契约

#### 目标

主题不再针对大量具体组件逐个编写 CSS 特例，而是针对稳定的组件类别和展示变体提供统一表现。

#### 注册层次

1. **呈现类别**：只描述主题需要处理的视觉骨架，不表达任务、日历、媒体等业务功能。
2. **展示变体**：描述同一组件内部会改变布局骨架、外壳关系或内容密度的稳定模式。
3. **组件专属覆盖**：只用于确实无法通过类别和变体表达的少数组件，不作为常规分类方式。

第一版已经注册 9 个主题呈现类别：

| 呈现类别 | 主题适配含义 | 当前组件示例 |
| --- | --- | --- |
| `collection` | 重复行、条目、卡片或时间线组成的内容流 | 最近文档、收藏、任务、最近日记、热搜、条件文档、复习文档、纪念日 |
| `metrics` | 少量关键数字和短标签组成的信息摘要 | 天气、统计卡片 |
| `visualization` | 图表、热力图、数据画布或查询结果 | 热力图、SQL 查询、可视化图表、数据库图表 |
| `editorial` | 阅读、书写或长文本优先的内容面 | 自定义文字、自定义文档、便签、每日一句、星座运势 |
| `media` | 图片、封面或播放内容占视觉主导 | 图片轮播、音乐播放器 |
| `control` | 单一操作目标明确的计时器或交互工具 | 专注计时、倒计时、赛博木鱼 |
| `embedded` | 由外部页面或隔离运行时主导的内容 | 网页浏览器 |
| `workspace` | 多区域、多状态、内部导航并存的复合工作台 | 固定资产、增强日记、记账、AI 知识库 |
| `intrinsic` | 自带完整造型、不适合被主题强行重排的仿真/自成形内容 | 时间日期、黄历 |

业务侧原有的 `kind` 暂时保留用于兼容，但内置主题已经优先从 `categories` 注册入口解析。新主题不应再根据 `task / calendar / chart` 等业务名称推测视觉结构。

第一版已登记以下会实际改变视觉骨架的展示变体：

- 最近日记：列表、日历。
- 纪念日：列表、紧凑、卡片、时间线。
- 天气：默认、简约 1、简约 2。
- 自定义文档：标准、紧凑、沉浸、自定义。
- 时间日期：经典、简约 1、简约 2、仿真表盘。
- 可视化图表：进度图、标签云。
- 便签：纯色、纹理。
- 数据库图表：折线、柱状、饼图、散点。
- 历史上的今天：列表、图片。
- 黄历：经典、传统。

数据来源、排序、筛选、颜色和轮播动画等不会改变组件视觉骨架的选项，不登记为主题展示变体，避免主题契约被业务配置污染。

#### 契约范围

- 外壳策略、背景、边框、阴影、圆角和内边距。
- 标题区是否显示、标题高度、操作区和内容区关系。
- 内容溢出、滚动容器、最小尺寸和宽高变化。
- 空状态、加载状态、错误状态和无权限状态。
- 标准、紧凑、沉浸等展示变体。
- 主题 token 与组件内部语义 token 的映射。

类别和变体已经由现有 Widget Definition 与 Theme Manifest 注册入口统一声明。运行时会暴露 `data-widget-presentation-category` 与 `data-widget-presentation-variant`，主题解析优先级为“展示变体 → 组件专属覆盖 → 呈现类别 → 旧 kind 兼容 → 通用回退”，不能通过散落选择器猜测组件类型。

- 加载进度必须由真实初始化阶段驱动，不能用计时器或动画模拟进度。

## P1｜明确要做的核心能力

### 5. Agent 临时智能工作台

#### 产品定位

允许用户通过自然语言，让 Agent 基于插件内置模板、数据源和安全动作，临时生成一组可以直接操作的卡片。它不是一段聊天回答，而是一次性生成的任务工作台、分析工作台或信息工作台。

示例：

- “把本周未完成任务和相关文档整理成一个工作台。”
- “显示最近一个月没有推进的项目，并列出下一步建议。”
- “汇总今天的日记、任务、专注记录和习惯完成情况。”
- “把最近阅读的文献、批注和对应思源文档放在一起。”

#### 预期体验

1. Agent 理解意图并选择一个内置工作台模板。
2. Agent 调用现有只读工具和数据服务获取真实数据。
3. 运行时生成受约束的工作台清单，而不是任意 HTML、CSS 或脚本。
4. 主页或 Agent 面板渲染真实卡片；卡片中的动作继续调用已注册的安全动作。
5. 用户可以继续用自然语言调整筛选、排序、分组和呈现方式。
6. 工作台默认是临时的；可以主动固定到主页或保存为可复用的智能视图。

#### 安全和架构边界

- Agent 只能从注册的模板、数据源、字段、视图和动作中组合工作台。
- 工作台结构建议使用 `AgentWorkbenchManifest` 一类声明式清单，至少包含模板、数据源查询、分组/排序、卡片类型、动作、有效期和权限信息。
- 禁止 Agent 生成和执行任意前端代码。
- 写操作继续走现有权限确认、预览、重复写防护和工具结果反馈。
- 临时工作台不复制任务、日记等业务数据，只保存查询和呈现清单。
- 固定到主页后，应作为一种正式组件类别/展示变体参与主题适配。

#### 分阶段建议

- 第一阶段：只读结果、固定模板、会话内临时存在。
- 第二阶段：允许调整视图并固定为智能组件。
- 第三阶段：开放受控写动作和与定时任务联动。

### 6. 强化日记工作台作为底层承载

#### 核心决策

晨间计划、晚间复盘、周期回顾等完整操作流程继续由“强化日记工作台”承载；主页不复制一套完整操作界面，只展示摘要、进度、提醒和进入对应操作的入口。

#### 主页应承担的内容

- 今日计划完成度、最重要事项和待处理项目。
- 昨日遗留、今日新任务、快速记录和待复盘数量。
- 当前日/周/月/年复盘状态。
- 晨间计划或晚间复盘尚未完成时的轻量提示。
- 点击具体摘要后，打开强化日记工作台并定位到指定日期、模块或操作步骤。

#### 实现边界

- 抽取无界面的强化日记领域服务和摘要 ViewModel，供主页组件、完整工作台和 Agent 共同使用。
- 主页不能通过隐藏挂载完整工作台来读取状态，也不能依赖工作台页面已经打开。
- 完整编辑、任务迁移、日记结构调整和复杂图表仍留在工作台。
- 主页摘要组件与工作台必须读写同一数据服务，不能维护第二份状态。
- 后续 Agent 临时工作台也可使用这些摘要和动作，但仍遵守工作台业务规则。

### 7. Agent 定时任务、心跳任务与后台执行

#### 产品方向

插件长期方向是 all-in-one AI 智能工作台。自动化不以用户手工搭建大量“触发器—条件—动作”规则为核心，而是让用户用自然语言要求 Agent 创建、修改、暂停和执行后台任务。

#### 任务类型

- **一次性定时任务**：在指定时间提醒、查询、整理或执行获批动作。
- **周期任务**：按日、周、月或 cron 计划执行固定目标。
- **心跳任务**：按可控频率检查状态；只有发现变化或达到条件时才进一步运行 Agent。
- **事件任务**：后续可监听插件内部事件，如任务完成、日记创建、专注结束或数据同步完成。

#### 体验要求

- 用户可以直接说：“每天晚上十点检查今天是否完成复盘，没有就提醒我。”
- Agent 将自然语言转换为可检查的任务清单，在创建前展示时间、目标、数据权限和可能执行的写操作。
- 提供统一任务中心，查看下次执行、上次结果、运行耗时、失败原因和消耗。
- 支持暂停、立即运行、修改、复制和删除。
- 任务运行后只在有结果、失败或需要确认时提醒，避免心跳任务产生通知噪音。

#### 安全与运行要求

- 后台任务必须保存为声明式 Job，不保存无法审查的任意执行代码。
- 每次运行具备唯一 ID、幂等保护、超时、重试上限、连续失败暂停和完整运行记录。
- 写操作必须遵守现有 Agent 权限策略；后台环境不能绕过需要确认的操作。
- 支持安静时段、并发限制、模型/额度限制和无网络恢复。
- 心跳先执行低成本确定性检查，只有命中条件才调用模型，避免持续消耗。

### 8. 高度自定义的全局日历组件

#### 产品定位

主页缺少一个跨业务模块的统一日历。该组件不是强化日记工作台日历的复制品，而是所有时间型信息的聚合视图和操作入口。

#### 数据源

- 强化日记：日记存在状态、计划、复盘、快速记录。
- 任务和任务管理 Plus：开始、截止、完成和延期信息。
- 习惯打卡：计划打卡、完成、补签和中断。
- 番茄钟：专注时段和累计时长。
- 纪念日、倒计时、提醒及其他后续注册的时间数据。
- 外部文献阅读、记账等模块可选择性提供时间事件，但默认不应让日历过载。

#### 统一事件接口

各业务模块通过 `CalendarEventProvider` 一类注册器提供事件，不让日历组件直接了解所有业务文件。事件应包含来源、类型、标题、时间范围、颜色语义、只读/可写能力、详情动作和跳转目标。

#### 展示与自定义

- 月视图、周视图、日程列表为基础视图；后续可增加年度热力视图。
- 用户可以选择数据源、事件类型、颜色、图标、显示字段、每格最大数量和溢出策略。
- 支持按项目、标签或业务类型建立过滤视图，并保存为组件配置。
- 不同主题通过“日历类别 + 月/周/列表变体”统一适配。
- 小尺寸组件优先显示摘要点、数量和主要事件；放大后逐步展开详情，不能把完整月历硬塞进狭小卡片。

#### 操作边界

- 点击事件可查看详情并跳转到对应工作台或来源文档。
- 支持能力由数据源声明；只读事件不能因为日历支持拖拽就被错误修改。
- 拖动改期、快速新增和跨日调整属于后续阶段，第一阶段先保证聚合显示、筛选和可靠跳转。

### 9. 习惯打卡系统与主页组件

#### 产品定位

习惯不是无限重复的普通任务。它需要独立的数据模型、计划规则、每日完成记录、连续性和趋势分析，并能够与日记、日历、番茄钟和 Agent 联动。

#### 习惯模型

- 名称、说明、图标、颜色和归档状态。
- 计划：每天、每周指定日期、每月次数、周期次数或自定义间隔。
- 打卡类型：完成/未完成、次数、时长、数值或等级。
- 目标值、最低有效值、允许补签、跳过规则和提醒时间。
- 可选关联项目、标签、日记字段或专注目标。

#### 打卡记录

- 每条记录保存习惯 ID、日期、结果、数值、备注、来源和修改时间。
- 区分完成、部分完成、跳过和未完成，避免“合理休息”被算作失败。
- 补签必须被标记，统计时可选择是否计入连续天数。

#### 主页体验

- 今日打卡：适合小卡片快速完成。
- 周期进度：显示本周目标、已完成次数和剩余次数。
- 连续记录：当前连续、最长连续和最近中断原因。
- 点击后进入习惯中心查看月历、趋势、记录和设置。

#### 联动

- 全局日历显示习惯计划和完成状态。
- 番茄钟可以绑定“阅读 25 分钟”等时长型习惯，专注结束后自动形成候选打卡。
- 强化日记可以插入今日习惯摘要和复盘问题。
- Agent 可以查询趋势、提醒异常和辅助制定习惯，但不能擅自补签或修改历史。

### 10. 高级番茄钟与专注数据中心

#### 现有基础

当前已经保存专注会话 ID、开始/结束时间、本地日期、计划时长、实际专注时长和完成/取消状态，并具有年度明细与汇总索引。升级应扩展现有专注数据体系，而不是重新建立一套计时记录。

#### 任务、项目和习惯绑定

- 开始专注前可以选择无绑定、任务、项目或习惯。
- 从任务或习惯入口启动时自动带入绑定对象。
- 会话记录增加稳定对象引用、对象类型和必要的标题快照；统计以稳定 ID 为准，标题快照只用于对象删除后的历史展示。
- 完成专注后，把实际时长计入对应任务、项目或时长型习惯。
- 任务详情能够查看累计专注时长、专注次数和最近一次专注。

#### 番茄钟能力升级

- 自定义专注、短休息、长休息和循环规则。
- 暂停、提前完成、取消、跳过休息及中断原因记录。
- 可选的专注目标、当前任务摘要和下一轮提示。
- 通知、声音、全屏/沉浸显示和迷你状态应继续遵守系统动画、音量和通知设置。

#### 专注数据中心

- 今日、周、月、年专注时长和完成次数。
- 按任务、项目、习惯、标签和时间段分析。
- 日历热力图、时段分布、专注时长趋势和完成率。
- 计划时长与实际时长偏差、取消原因和中断分布。
- 最近会话明细，可跳转到绑定对象。
- 数据中心是完整分析入口；主页番茄钟组件只保留当前计时、今日摘要和快速开始。

## P2｜明确保留、逐步推进

### 11. 数据库数据转图表组件

#### 当前状态

项目已经存在 `databaseChart` 渲染器、组件注册、ECharts 实现和部分配置字段；桌面端内容设置中的类型入口和设置组件被注释隐藏。后续不是简单取消注释，而是以当前数据库结构、主题契约和移动端配置方式重新整理后再开放。

#### 目标能力

- 选择一个思源数据库/属性视图作为数据源。
- 选择分类、数值、日期等字段，并对字段类型进行明确校验。
- 支持直接数值、计数、求和、平均、最大/最小和按时间分组。
- 支持折线、条形、饼图，以及后续适合日期和分布数据的图表。
- 支持排序、筛选、空值处理、Top N、图例、标签和提示框配置。
- 图表点击后可以查看来源行或跳转到对应文档。
- 图表颜色、字体、背景和交互状态接入主题图表 token，不能在组件中固化一套颜色。
- 数据较大时先在服务层聚合，避免把全部属性视图数据直接交给 ECharts。

#### 架构方向

将“数据源—字段映射—聚合转换—图表呈现”拆开。数据库图表是第一个使用者，未来统计组件、Agent 临时工作台和外部文献组件也可以复用同一可视化管线。

### 12. 文献阅读数据组件与思源同步

> 用户当前称为 Rotelo 文献阅读软件；具体产品名称、可用 API 和授权方式在实现前确认。若实际目标为 Zotero，则按 Zotero 的正式数据接口和本地能力设计。

#### 产品定位

这是一个独立的文献数据集成和展示组件，不把第三方 MCP 直接安装到当前 Agent，也不让 Agent 负责文献库管理。

#### 展示能力

- 文献总数、分类/集合数量和分类分布。
- 最近阅读、最近新增、最近修改的文献。
- 文献的批注、笔记数量和最近笔记摘要。
- 阅读趋势、来源年份、作者、标签和文献类型等统计。
- 点击文献后打开来源软件、查看详情或打开已同步的思源文档。

#### 思源同步

- 将文献元数据、摘要、批注和笔记同步到用户指定的思源笔记本或父文档。
- 每条外部文献保存稳定来源 ID 与思源文档 ID 映射，保证重复同步不会重复创建。
- 明确同步方向；第一阶段建议以外部文献库到思源为主，不贸然做双向编辑。
- 支持同步预览、手动同步、增量同步、冲突提示、失败重试和同步记录。
- 用户可以选择文档模板、字段映射、笔记组织方式和是否同步附件链接。

#### 架构边界

- 外部连接、授权、读取、缓存和同步逻辑属于独立文献服务，不写在主页组件内部。
- 主页组件只消费标准化的文献摘要数据和同步状态。
- 后续可以把只读查询能力注册给 Agent，但这不是第一阶段目标，也不能成为组件可用的前提。

### 13. 内容对象右键动作

- 方向可以考虑，但需要结合每个组件内部的对象模型逐步接入，不要求一次覆盖所有组件。
- 第一批优先考虑最近文档、收藏文档、任务、任务管理 Plus、最近日记和复习文档。
- 组件通过对象适配器暴露稳定 ID、对象类型、标题、来源和支持动作。
- 普通右键优先处理内容对象；`Alt + 右键`继续作为强制打开组件菜单的统一方式。
- 动作由业务模块注册，例如打开、收藏、转为任务、加入今日计划、开始专注、交给 Agent、复制链接。
- 自定义文档和便签等编辑器区域不强行接入对象菜单，继续尊重编辑器自身右键行为。

## 明确暂缓或不考虑

### 插件自建全局命令面板

- 思源已有命令面板，插件再实现一套价值有限。
- 高频功能已有快捷键，熟练用户的主要问题不是缺少新的命令入口。
- 如果以后需要增强发现性，优先把主页功能注册到思源现有命令体系。

### 桌面端布局编辑模式增强

- 当前不作为近期开发方向。
- 项目已经有布局模板，多选、对齐、等宽等增强目前收益不足。
- 不新增常驻悬浮按钮或破坏默认页面清爽度的编辑控件。

### 单独建设全局快速预览与就地处理体系

- 当前预览框已经内置编辑器，用户可以直接查看和编辑文档。
- 重新建设一套统一快速预览的真实新增场景有限，暂不作为独立产品方向。
- 后续只针对现有预览框出现的实际问题做增强，不为了统一形式重写。

### 以手工规则配置为核心的自动化中心

- 跨组件自动化有价值，但不优先让用户配置大量触发器、条件和动作。
- 自动化优先围绕 Agent 定时任务、心跳任务、事件任务和自然语言配置展开。
- 底层仍需要确定性的调度和动作注册，但这些复杂性不必直接暴露给普通用户。

### 上下文镜头/场景过滤系统

- 同一布局为工作、学习、阅读等场景逐个配置数据过滤条件，配置成本较高。
- 预计愿意完整配置的用户有限，当前投入产出比不足。
- 后续如果 Agent 可以自动生成并维护场景配置，再重新评估。

## 其他组件高级化建议（尚待确认）

### 复习文档 → 复习中心

- 从简单复习计划升级为每日复习队列、逾期积压和周期统计。
- 支持按文档重要度、复习结果和遗忘程度调整下次复习时间。
- 记录“记得、模糊、忘记”等结果，展示保留率、积压趋势和最薄弱主题。
- 后续可让 Agent 基于文档生成复习问题，但复习计划本身保持确定性。

### 快速便签/快速记录 → 统一收集箱

- 将未处理的便签和快速记录集中为收集箱，而不是长期堆在多个组件里。
- 支持转换为文档、任务、习惯、日记记录或归档。
- Agent 可以辅助分类和提出转换建议，但用户确认后才执行写操作。

### 任务管理 Plus → 项目驾驶舱

- 将任务、子任务、项目进度、截止时间、专注时长和阻塞状态关联起来。
- 增加项目健康度、长期未推进任务、即将到期事项和工作量分布。
- 与全局日历、番茄钟和 Agent 临时工作台共享同一任务/项目数据服务。

### 纪念日/倒计时 → 里程碑中心

- 允许里程碑关联项目、任务和阶段完成度，而不只是显示剩余天数。
- 展示当前阶段、已完成事项、下一关键节点和时间风险。
- 仍保留纯纪念日模式，不强迫所有倒计时进入项目体系。

### 统计卡片、热力图、可视化图表 → 统一分析能力

- 统一数据源、日期范围、筛选、聚合和主题图表 token。
- 主页小组件负责摘要，完整数据中心负责钻取和比较。
- 让数据库图表、习惯、番茄钟、任务和文献模块复用同一分析管线，避免每个组件重新实现日期筛选和图表样式。

### 记账与固定资产 → 个人财务中心

- 在现有流水和资产基础上增加预算、周期账单、账户趋势和净资产变化。
- 主页只展示关键异常和摘要，完整分析进入财务中心。
- 此项尚未由用户确认优先级，不能挤占已经明确的 AI、日历、习惯和番茄钟方向。

## 建议实施顺序

该顺序同时考虑用户明确意愿和技术依赖，不代表必须一次全部完成：

1. 完成 P0 基础：设置搜索、组件呈现契约和性能观测。
2. 建设 Agent P0 内核：统一 Profile/错误协议、上下文清单、执行检查点和第一批真实失败 eval。
3. 用 10/30/100 轮上下文、工具故障和写操作最终状态评测验证 Agent；同步完成执行状态与恢复 UI。
4. 建设结构化个人记忆及候选、整理、冲突、确认、检索、遗忘生命周期。
5. 将对话、状态语、选中文字和机器人接入统一 Profile、诊断和权限协议。
6. 抽取强化日记领域服务，让主页摘要、完整工作台和 Agent 共用同一底层。
7. 建设主页 Agent 能力注册层，以及今日简报、建议收件箱和临时智能工作台第一阶段。
8. 建设 LLM Wiki / AI 知识管家首期：AI 元数据、知识地图、治理建议和带引用简报。
9. 建设 Agent 后台 Job 模型，以及一次性定时任务、周期任务和低成本心跳。
10. 建设统一日历事件提供者，并实现全局日历第一阶段。
11. 建设习惯领域数据模型和今日打卡组件。
12. 扩展现有专注会话，完成任务/项目/习惯绑定与专注数据中心。
13. 重构数据库图表的数据源和转换管线后重新开放。
14. 确认目标文献软件及接口，开发独立文献服务、展示组件和单向思源同步。
15. 按组件逐步增加内容对象动作，并评估其他组件高级化候选。
